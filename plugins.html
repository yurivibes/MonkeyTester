Plugins

Test Plugins
Test Plugins run the tests: the esp32-* device plugins own the hardware, and monkeytester-ai is the vision-model plugin. Each is a standalone HTTP service implementing PLUGIN_API.md (contract monkeytester-plugin), kept in its own repo — the viewer holds no hardware code. The Build Plugin section below belongs to Build & Test, not to tests.
How to configure a Test Plugin
  • A plugin is a standalone HTTP service implementing PLUGIN_API.md (contract monkeytester-plugin), kept in its own repo — the viewer holds no hardware code.
  • Device plugins are registered here, in the Manage device plugins box: the list lives in Run/config.json as a plugins map {name: url}. On the first viewer start, entries of the environment variable VT_PLUGINS=name=url[,name=url] are imported into that map once, after which the variable is ignored — Settings owns the list. The monkeytester-ai plugin is separate: its address is only set in that row's Configure panel (Plugin address field) and saved in Run/config.json as visual_plugin_url. When the MonkeyTester Mac app runs the viewer, it supplies that address and the pairing token itself (VT_MANAGED_AI_PLUGIN_URL + VT_MANAGED_AI_PLUGIN_TOKEN): the row then shows the address read-only with “Managed by the MonkeyTester app”.
  • On Linux, run the plugin as a systemd user service (its own repo ships the unit). Register it in Manage device plugins after a viewer start; entries an existing visualtest-viewer.service.d/plugins.conf drop-in still sets via Environment=VT_PLUGINS=… are imported into Settings once, so the drop-in no longer needs to list plugins.
  • If a plugin is started with a token (its own PLUGIN_TOKEN), give the viewer the same value in Settings → Configuration → Service tokens (admins): it is checked against the plugin's GET /devices, stored in service_tokens.json (mode 0600) and sent as X-Plugin-Token. The old PLUGIN_TOKEN / VT_PLUGIN_TOKEN_<NAME> environment variables are imported there once, then ignored. A missing or wrong token shows here as a 401 error.
  • The monkeytester-ai row always shows a Configure button, even with no plugin set yet. Its panel is laid out in two sections, Plugin on top (plugin address field, the Plugin keep/remove select, the Token select and the write-only token status), then Configuration below it (provider radios, model dropdowns, the Remote server subsection, the Copilot select) with the single Save changes button as the LAST element at the bottom of the Configuration section. It edits everything through fields — Plugin address, pairing-token paste, the Local model/Remote server/GitHub Copilot provider radios, the remote server's address, model, resize switch and API key — and ONE Save changes button applies all pending edits in the plugin's required order (pairing-token op first, then the plugin address — including a staged “Remove plugin” choice —, then the remote keys in one request, then the provider last). The button stays greyed while nothing differs from the saved state. Token Set/Replace/Remove, plugin removal and Copilot sign in/out are staged selects, not buttons: any armed choice marks the panel dirty and the single Save executes it; only Load models and Refresh list stay as buttons (fetches — Load models validates, and thereby saves, the typed remote address: the plugin contract only lists remote models of a saved address). Choose Local model (one of the plugin's installed models), Remote server (an OpenAI-compatible server such as llama-server, with an optional API key — that server's address is a different thing from the plugin address) or GitHub Copilot (sign in with GitHub, then pick a vision model). The plugin stores the remote API key and the GitHub sign-in and forwards vision calls; the viewer stores neither.
  • Add and Save address only store an address whose service answers GET /health with the monkeytester-plugin contract at a supported version — a refused save shows the plugin's own error. Remove forgets a registration (and its token). Plugin tokens are set in Settings → Configuration → Service tokens.
  • Tests call a plugin with steps like PLUGIN: esp32 factory-reset; the name must match a registered plugin name (Settings → Plugins, Test Plugins).
Build Plugin
Build & Test builds a branch of your app on a build plugin's own host — a Mac builds Android and iOS, a Linux host Android only — and tests the result on the devices. A build plugin is a separate service that fetches the branch from Gitea or GitHub, runs the app repo's build scripts there and uploads the apps back to the viewer. The plugin holds the code host's address and read-only token; the viewer never sees that token.
How to configure a build plugin
  • The local build tool is build-local at http://127.0.0.1:8094: it builds on its own host — a Mac builds Android and iOS, a Linux host Android only. Add registers it: the address is saved only when the plugin's GET /health answers with the build plugin contract (BUILD_PLUGIN_API.md, contract monkeytester-build-plugin) — a refused save shows the plugin's own error.
  • Build plugins live in the SAME Run/config.json plugins map as the Test Plugins above, as object entries {name: {url}} (a plain url string is a Test Plugin). Add takes a pairing token only if the plugin was started with its own PLUGIN_TOKEN; leave it blank when editing to keep the saved one. The token is stored in service_tokens.json (mode 0600), not in config.json, and can also be replaced in Settings → Configuration → Service tokens. On the first viewer start, entries of VT_BUILD_PLUGINS=name=url[,name=url] are imported into the map once, after which Settings owns the list.
  • Save address edits a registered plugin's address; Remove forgets a registration — refused while a Build & Test project still uses that plugin.
  • Click Configure on the card for the plugin's code host settings: Code host (Gitea or GitHub), its URL, a read-only token (paste; sent to the plugin, which checks it with the code host before saving — stored by the plugin only, mode 0600, never shown again; the scopes it needs — Gitea read:repository + read:user, GitHub fine-grained Contents: read + Metadata: read, or a classic repo token for private repos — are in the plugin's README) and the Viewer URL the plugin uploads built apps to, prefilled with the address you are using now. Save stays greyed while nothing differs from the saved state; Remove token appears once one is saved.
  • The repos themselves live on Settings → Build & Test: each project picks a build plugin from this registry and a branch; the check column shows whether the plugin can read the repo and whether that branch has the platform's build script (.monkeytester/build-android.sh, .monkeytester/build-ios.sh).
